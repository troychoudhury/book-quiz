## 🔴 Critical Findings (Blockers)

### 1. Hardcoded Secrets and Credentials in Source Code
- **Vulnerability Type**: Hardcoded Secrets (OWASP A07:2021 – Identification and Authentication Failures)
- **Location**: `backend/app/core/config.py:17,22,35`
- **Impact**: The source code contains hardcoded default credentials that will be used if environment variables are not explicitly set. If an attacker gains read access to the source code (e.g., via a misconfigured repository, leaked source, or insider threat), they obtain:
  - **JWT signing secret** (`"change-me-in-production-use-a-real-secret"`) — allows forging valid JWT tokens for any user, bypassing all authentication.
  - **Database credentials** (`bookquiz:bookquiz_dev@localhost:5432/bookquiz`) — allows direct database access if network controls are also misconfigured.
  - **Admin API key** (`"admin-dev-key-change-me"`) — allows access to any admin-privileged endpoints.
  - Even though these can be overridden via environment variables, their presence as defaults in code is a supply-chain risk. If `.env` is ever accidentally committed or a deployer forgets to override, the application boots with known-compromised credentials.
- **Remediation**:
  - Remove all hardcoded credential defaults from `config.py`. Use `None` or empty strings for secrets, and enforce that they are provided at startup (e.g., `assert settings.jwt_secret_key, "JWT_SECRET_KEY is required"`).
  - For `database_url`, use a placeholder like `"postgresql://localhost:5432/bookquiz"` without credentials, or raise on missing value.
  - Rotate any secrets that may have been exposed in git history (the repo is new, but this is a best practice).
  - Add `.env` to `.gitignore` (already present ✓) and add `**/config.py` secrets patterns to secret scanning tools.

### 2. Information Disclosure via Error Messages
- **Vulnerability Type**: Security Misconfiguration / Information Leakage (OWASP A05:2021)
- **Location**: `backend/app/main.py:67`
- **Impact**: The generic exception handler returns `error_type: type(exc).__name__` in the JSON response body. This exposes internal Python exception class names (e.g., `IntegrityError`, `ProgrammingError`, `OperationalError`) to API consumers. An attacker can use this information to:
  - Map the technology stack (SQLAlchemy, PostgreSQL, Redis, etc.)
  - Identify database schema details through `IntegrityError` messages
  - Craft targeted attacks based on the specific error types
- **Remediation**:
  - Remove `error_type` from the production error response.
  - Only include error detail in `debug=True` mode.
  - In production, return a generic `{"detail": "An unexpected error occurred."}` without internal class names.
  - Log the full exception details server-side using `structlog` (already in use).

### 3. Missing Authentication Enforcement on Protected Endpoints
- **Vulnerability Type**: Broken Access Control (OWASP A01:2021)
- **Location**: `backend/app/api/profile.py:16-33`, `backend/app/api/quiz.py:29-55`, `backend/app/api/auth.py:56-87`
- **Impact**: The application has **no authentication middleware or dependency injection** that verifies JWT tokens on protected routes:
  - The `/api/v1/users/me/profile` endpoint (profile.py:16) is a stub that explicitly states it "requires authentication middleware to resolve user from JWT" — the middleware does not exist.
  - Quiz endpoints (`quiz.py`) accept `user_id=None` for all attempts as "guest" — but there is no mechanism to link a guest attempt to an authenticated user after login.
  - The `refresh` endpoint (auth.py:72) does not invalidate old refresh tokens, meaning a stolen refresh token can be used indefinitely until it expires (7 days).
  - There is no token revocation mechanism or blacklist for refresh tokens.
- **Remediation**:
  - Implement a `get_current_user` FastAPI dependency that verifies the JWT from the `Authorization: Bearer <token>` header and returns the authenticated user.
  - Add this dependency to all protected routes.
  - Implement refresh token rotation: issue a new refresh token on each refresh and invalidate the old one (store a `token_version` or `jti` blacklist in Redis).
  - For guest quiz attempts, use a server-generated anonymous session ID (stored in an httpOnly cookie or short-lived token), and provide a "claim" endpoint for authenticated users to link guest attempts.

## 🟠 High Severity

### 4. JWT Tokens Stored in localStorage — XSS Vulnerable
- **Vulnerability Type**: Sensitive Data Exposure (OWASP A02:2021)
- **Location**: `frontend/src/stores/authStore.ts:22-23`, `frontend/src/services/api.ts:13,49,57-58`
- **Impact**: Both access and refresh tokens are stored in `localStorage`, which is accessible to any JavaScript running on the page. If an XSS vulnerability exists (or is introduced later via a dependency), an attacker can steal both tokens and impersonate the user. The `withCredentials: true` setting in axios (api.ts:8) and the remark about "httpOnly refresh cookies" suggest the intent was to use secure httpOnly cookies, but the backend never sets them — tokens are only returned in JSON response bodies.
- **Remediation**:
  - **Preferred**: Store the refresh token in an httpOnly, Secure, SameSite=Strict cookie set by the backend. Store only the access token in memory (not localStorage) and use the httpOnly cookie to silently refresh.
  - **Alternative** (if httpOnly cookies are not feasible): Use a BFF (Backend-for-Frontend) pattern where the frontend never directly handles tokens.
  - At minimum, use sessionStorage instead of localStorage for the access token (cleared on tab close), but this is still vulnerable to XSS.

### 5. No Rate Limiting on Authentication Endpoints
- **Vulnerability Type**: Identification and Authentication Failures (OWASP A07:2021)
- **Location**: `backend/app/api/auth.py:42-55` (register), `backend/app/api/auth.py:56-70` (login), `backend/app/api/auth.py:72-87` (refresh)
- **Impact**: The `/api/v1/auth/login` and `/api/v1/auth/register` endpoints have no rate limiting. An attacker can:
  - Brute-force passwords against known email addresses
  - Enumerate valid email addresses via timing differences in error responses
  - Perform credential stuffing attacks
  - Exhaust resources through mass account creation
- **Remediation**:
  - Implement rate limiting using a library like `slowapi` (Redis-backed) or a middleware approach.
  - Apply stricter limits to `/login` (e.g., 5 attempts per IP per minute) and `/register` (e.g., 3 per IP per hour).
  - Add progressive delays (exponential backoff) on repeated failed attempts.
  - Ensure error responses for invalid email vs. invalid password are identical in timing and content (the current code already returns the same message `"Invalid email or password."` — ✓ good).

### 6. Backend API Missing Critical Security Headers
- **Vulnerability Type**: Security Misconfiguration (OWASP A05:2021)
- **Location**: `backend/app/main.py:27-42` (CORS setup and middleware chain)
- **Impact**: The backend API does not set any of the following critical security headers:
  - `Strict-Transport-Security` (HSTS) — missing; allows SSL stripping attacks
  - `X-Content-Type-Options: nosniff` — missing; allows MIME type sniffing
  - `X-Frame-Options: DENY` — missing; allows clickjacking of API responses (if rendered in browser)
  - `Content-Security-Policy` — missing; allows content injection
  - `Cache-Control` for sensitive responses — missing; tokens could be cached by intermediate proxies
  - Note: The frontend nginx config (`frontend/nginx.conf:14-18`) does set these headers for static assets — good. But the backend API that serves JSON responses does not.
- **Remediation**:
  - Add a security headers middleware to FastAPI that sets these headers on all responses.
  - For auth endpoints specifically, add `Cache-Control: no-store` to prevent token caching.
  - Set HSTS with `max-age=31536000; includeSubDomains` in production.

### 7. Quiz Answer Correctness Leaked via API Response
- **Vulnerability Type**: Broken Access Control / Information Leakage
- **Location**: `backend/app/api/quiz.py:98-99` (`answer_question` endpoint returns `is_correct` and `correct_choice_id`)
- **Impact**: The `/api/v1/quizzes/{attempt_id}/answer` endpoint returns whether the submitted answer is correct and the ID of the correct choice. A malicious client could:
  - Submit every possible choice to discover the correct answer (4 choices × 10 questions = 40 requests max)
  - Achieve 100% scores programmatically without any knowledge of the book
  - The `is_correct` boolean provides an oracle for brute-forcing answers
  - This undermines the entire quiz integrity model
- **Remediation**:
  - Do not return `is_correct` or `correct_choice_id` during the quiz session. Accumulate answers server-side and only reveal correctness on quiz completion.
  - Alternatively, accept this design but add server-side validation: enforce that each question can only be answered once per attempt, track the sequence, and prevent re-answering. The current code does enforce one-answer-per-question implicitly (each call creates a new `QuizAnswer` row), but does not check for existing answers to the same question in the same attempt before inserting.

## 🟡 Medium/Low Findings

### 8. CORS Configuration is Overly Permissive
- **Location**: `backend/app/main.py:39-42`
- `allow_methods=["*"]` and `allow_headers=["*"]` are unnecessarily broad. While `allow_credentials=True` with wildcard origins would be blocked by modern browsers, explicit wildcards in methods/headers increase the attack surface.
- **Remediation**: Restrict to needed methods (`["GET", "POST", "PUT", "DELETE", "OPTIONS"]`) and headers (`["Content-Type", "Authorization"]`).

### 9. Weak Password Policy — Minimum Length Only
- **Location**: `backend/app/api/auth.py:14`
- `password: str = Field(..., min_length=8, max_length=128)` — only enforces minimum length. No requirement for uppercase, lowercase, digits, or special characters. Passwords like `aaaaaaaa` or `password` pass validation.
- **Remediation**: Add a regex validator or use a library like `zxcvbn` for password strength estimation. Require at least 3 of 4 character classes (uppercase, lowercase, digit, special).

### 10. No Refresh Token Rotation / Reuse Detection
- **Location**: `backend/app/api/auth.py:72-87`, `backend/app/services/auth_service.py:53-57`
- Refresh tokens are stateless JWTs. Once issued, they are valid for 7 days with no mechanism to revoke them. If a refresh token is stolen, the attacker can continuously obtain new access tokens. There is no token family or rotation.
- **Remediation**: Implement refresh token rotation: on each use, invalidate the old refresh token and issue a new one. Store a `token_version` on the User model or maintain a Redis-based allowlist/denylist.

### 11. No CSRF Protection on State-Changing Endpoints
- **Location**: All POST/PUT/DELETE endpoints in `backend/app/api/`
- Since the authentication mechanism uses a Bearer token from localStorage (not cookies), CSRF is partially mitigated by the fact that the token must be explicitly attached. However, if the token storage is changed to cookies, CSRF protection becomes critical.
- **Remediation**: If switching to cookie-based auth, implement CSRF tokens (e.g., double-submit cookie pattern).

### 12. User Enumeration Risk via Registration
- **Location**: `backend/app/api/auth.py:46-52`
- The registration endpoint returns `409 Conflict` with `"A user with this email already exists."` — this explicitly confirms whether an email is registered, enabling user enumeration.
- **Remediation**: If preventing enumeration is important, return a generic message like `"If the email is not already registered, a confirmation will be sent."` or use email verification flow. Note: this is a UX trade-off; many apps accept this risk.

### 13. No Security Logging for Authentication Events
- **Location**: `backend/app/api/auth.py`, `backend/app/services/auth_service.py`
- Failed login attempts, successful logins, registrations, and token refresh operations are not logged. This hinders incident response and breach detection.
- **Remediation**: Log all auth events (login success/failure, registration, token refresh, password change) with `structlog`, including IP address and user agent (but not passwords or full tokens).

### 14. Missing Alembic Migrations Directory
- **Location**: `backend/` — no `alembic/` or `migrations/` directory found
- While the CI/CD pipeline references `alembic upgrade head` (ci.yml:162), there is no migrations directory. Database tables would only be created if `Base.metadata.create_all()` is called, which is not recommended for production. This is more of a missing feature than a vulnerability, but it indicates incomplete database lifecycle management.
- **Remediation**: Initialize Alembic and create an initial migration for the models.

### 15. Frontend: No Input Sanitization for Dynamically Rendered Content
- **Location**: `frontend/src/pages/QuizPage.tsx:104-117`, `frontend/src/pages/LandingPage.tsx:35-37`
- Quiz question text and choices are rendered directly as React children (which React escapes by default — ✓). However, if any future code uses `dangerouslySetInnerHTML` to render book descriptions or AI-generated question text, it would be vulnerable to XSS. The AI-generated question text is a potential vector since it comes from an external API (OpenAI).
- **Remediation**: If `dangerouslySetInnerHTML` is ever used, wrap content with DOMPurify first. Consider sanitizing/escaping AI-generated content at the API boundary.

### 16. Frontend: No Redirect Validation After Login
- **Location**: `frontend/src/services/api.ts:66`
- On refresh token failure, the code does `window.location.href = '/login'` — this is a hard redirect. If there's an `open redirect` vulnerability on the login page (e.g., `?redirect=...`), an attacker could chain this. This is currently low risk but worth noting.
- **Remediation**: Validate any redirect URLs against an allowlist of same-origin paths.

### 17. Dockerfile: Non-Root User (Good Practice — Verified ✓)
- **Location**: `backend/Dockerfile:9-14`
- The backend Dockerfile properly creates and uses a non-root `bookquiz` user. The frontend nginx image runs as `nginx` user by default. Both are good practices.

### 18. CI/CD: Secrets Handling in CI Workflow
- **Location**: `.github/workflows/ci.yml:74`
- `OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}` is passed as an environment variable for tests. This is standard practice. However, test database credentials (`bookquiz:test_pass`) are hardcoded in the workflow YAML — this is acceptable for ephemeral test services but should not be reused in production.
- **Remediation**: Ensure CI test credentials are never the same as any production credentials.

## ✅ Clean Areas

- **SQL Injection Prevention**: All database queries use SQLAlchemy ORM with parameterized queries. No raw SQL string concatenation detected. ✓
- **Password Hashing**: Uses `passlib` with `bcrypt` (via `CryptContext(schemes=["bcrypt"])`). Industry-standard practice. ✓
- **.gitignore**: Properly configured to exclude `.env`, `node_modules`, `__pycache__`, and test artifacts. ✓
- **Frontend nginx Security Headers**: The nginx reverse proxy config sets `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, and `Content-Security-Policy`. ✓
- **JWT Algorithm**: Hardcoded to `HS256` via config (not accepting `alg: none` from token header). `python-jose` validates this correctly. ✓
- **E2E Tests**: Playwright tests exist and cover the landing page. Authentication acceptance tests cover registration, login, and token refresh flows. ✓
- **No `eval()` or `dangerouslySetInnerHTML`**: No dynamic code execution or unsanitized HTML rendering detected in frontend. ✓
- **CI Security Scan**: CI workflow includes Snyk scanning for both backend and frontend dependencies. ✓
- **HTTPS Enforcement**: `fly.toml` has `force_https = true` for the production deployment. ✓

- **Recommendation**: When dependency files are created, run `pip-audit` or `safety` (Python) and `npm audit` (Node.js) to establish a baseline. Pin exact versions in lock files. The CI already includes Snyk scanning which is good.
